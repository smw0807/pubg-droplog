# 듀오와 스쿼드 복기 서비스 구현 시작 프롬프트

새 저장소의 `docs/PUBG_SQUAD_REVIEW_PRD.md`에 기획서를 넣은 뒤 아래 프롬프트를 Codex 작업에 전달하세요. 이 파일을 `docs/CODEX_START_PROMPT.md`로 함께 보관해도 됩니다. 제품 가칭과 저장소 이름이 달라도 구현을 시작할 수 있습니다.

## 전달할 프롬프트

```text
docs/PUBG_SQUAD_REVIEW_PRD.md를 읽고 이 저장소에 PUBG 듀오·스쿼드 복기 서비스를 구현해줘.

지원 범위는 3인칭(TPP)의 일반 듀오·일반 스쿼드·랭크 듀오·랭크 스쿼드야.
1인칭(FPP), 솔로, 커스텀·아케이드·훈련·이벤트 경기는 제외해.
사용자 흐름은 닉네임 검색 → 일반/랭크와 듀오/스쿼드 필터 → 경기 선택
→ 팀 성적표와 이벤트 타임라인 → 링크 공유야.
기획서의 MVP를 완료할 때까지 단계별로 구현하고 검증해줘.

확정된 기술 선택:
- Nuxt 4의 화면과 Nitro server API를 한 저장소에서 사용한다.
- Nuxt UI 4와 Tailwind CSS 4로 UI를 만든다.
- PUBG API 조회는 서버 전용 pubg-kit 어댑터를 사용한다.
- PostgreSQL과 Drizzle ORM으로 정규화한 리포트를 저장한다.
- TypeScript strict, pnpm, 호환되는 지원 중 Node LTS를 사용한다.
- 별도 NestJS 서버는 만들지 않는다.
- 초기 검증 환경은 Nitro Node 서버 단일 프로세스다.

먼저 저장소 상태와 AGENTS.md를 확인해줘. 기존 변경을 보존하고,
빈 저장소라면 필요한 프로젝트 파일을 생성해줘.
실제로 호환되는 의존성 버전을 확인해 고정하고 packageManager와 lockfile을 관리해줘.
구현 계획만 제시하고 끝내지 말고 T01부터 실제 파일을 작성해줘.

구현 순서:
1. 프로젝트 기반, Nuxt UI 테마, 공개 DTO, 합성 fixture, pubg-kit 동작 확인.
2. API 키 없이 사용할 수 있는 demo 모드, 네 TPP 조합 샘플, 3개 화면과 모드 필터.
3. PostgreSQL Docker Compose, 마이그레이션, Repository와 저장 결과 재조회.
4. PUBG 어댑터, 입력 검증, 호출 제한, 오류 처리, 취소와 용량 제한.
5. 순수 분석 함수, 공식 통계와 이벤트의 분리, 부분 리포트, 중복 분석 방지.
6. 전체 흐름 통합, 공유 직접 접근, 핵심 테스트, 생산 빌드 Nitro 실행 검증.
7. 유효한 키가 설정되어 있으면 실제 일반·랭크 분류값과 조합별 읽기 전용 검증, 성능 기록.

중요한 구현 규칙:
- 상세 범위와 수용 기준은 기획서를 따른다.
- server/api에는 HTTP 처리만 두고 분석은 네트워크·DB와 분리된 순수 함수로 만든다.
- pubg-kit을 클라이언트에서 import하거나 API 키를 public runtimeConfig에 넣지 않는다.
- 설치한 pubg-kit 버전의 limiter, cache, telemetry 타입과 검증 동작을 직접 확인한다.
- SDK rateLimit을 끌 때는 제한 대상의 API키당 호출 제어를 함께 구현하고 테스트한다.
- 원본 텔레메트리를 무제한 캐시하지 않는다.
- 안전한 텔레메트리 전송을 SDK로 보장할 수 없으면 그 다운로드 부분만
  좁은 서버 fetch 어댑터로 보완하고 이유를 기록한다.
- 매치 스키마 검증 오류로 누락 통계를 처리할 수 없을 때에는 기획서의
  공식 match 전용 호환 경로를 사용한다. 네트워크 오류를 같은 예외로 재요청하지 않는다.
- 공식 매치 asset에서 얻은 URL만 검증해 사용한다. 임의 URL 프록시를 만들지 않는다.
- 정규화 전 입력은 unknown으로 검증한다. any나 무조건 타입 단언으로 숨기지 않는다.
- account ID, participant ID, roster ID를 구분한다.
- matchType과 gameMode를 별도로 보존하고 일반/랭크, 듀오/스쿼드, 시점을 정규화한다.
- 초기 gameMode 허용값은 duo와 squad이며 -fpp 값은 목록과 리포트 생성 양쪽에서 거부한다.
- matchType 초기 매핑 official→normal, competitive→ranked는 실제 응답으로 확인한다.
  원본 gameType 필드를 가정하거나 누락된 matchType을 임의로 일반전으로 처리하지 않는다.
- 듀오는 실제 1~2명, 스쿼드는 실제 1~4명을 표시한다. 2인 스쿼드를 듀오로 바꾸지 않는다.
- 일반/랭크와 듀오/스쿼드 교차 필터를 URL과 커서에 연결한다.
  일부 묶음의 필터 결과가 0개여도 다음 원본이 남아 있으면 더 보기를 유지한다.
- 랭크 듀오를 구현 범위에서 제외하지 않는다. 실제 기록이 없는 플랫폼·조합은
  조회 범위의 데이터 없음 또는 미검증으로 기록하고 다른 모드로 대체하지 않는다.
- 개인·팀 성적표는 공식 경기 통계를 사용한다. 텔레메트리 합계로 덮어쓰지 않는다.
- killer, finisher, 기절 유발자를 구분한다. 첫 사망을 최종 전멸로 단정하지 않는다.
- 누락값은 0으로 만들지 않고 부분 리포트와 확인 불가 상태를 제공한다.
- 경기 ID 배열 순서를 최신순으로 가정하지 않는다.
- 저장 완료 리포트는 재사용하고 같은 분석 요청은 합친다.
- demo와 live를 명확하게 분리하며 live 실패를 샘플 성공으로 바꾸지 않는다.
- 저장 출처와 캐시 키에 source를 포함하고 모드 변경 후에도 샘플 표시를 보존한다.
- Nuxt UI 테마와 컴포넌트를 일관되게 사용한다. 모바일 성적표는 카드로 표시한다.
- 초기 기능에 1인칭, 솔로, 시즌 티어 대시보드, 로그인, AI 코칭, 지도 재생, 자동 교전 분리, Redis, BullMQ,
  차트 라이브러리, 별도 API 서버를 추가하지 않는다.

검증과 인계:
- 단계별로 필요한 lint, typecheck, 단위·DB통합·브라우저 테스트와 build를 실행해줘.
- 빌드 통과만으로 API 성공을 판단하지 말고 실제 빌드된 Nitro 경로도 확인해줘.
- docs/progress.md에 단계 상태와 다음 작업을 기록해줘.
- docs/validation.md에 명령과 실제 결과, fixture/live 구분,
  의존성 버전, 측정 환경, 미검증 항목을 기록해줘.
- README에 설치, DB 실행, 환경변수, demo 실행, live 검증 절차를 적어줘.
- 실제 키가 없으면 demo와 mock 검증으로 가능한 구현을 계속하고,
  실제 PUBG 연동과 운영 환경은 미검증이라고 명시해줘.
- 비밀값을 채팅·로그·소스·Git에 출력하지 마.
- 공개 배포, 유료 리소스 생성, 기존 데이터 삭제는 별도 요청 없이 실행하지 마.

작업 마지막에는 구현된 기능, 실행 방법, 검증 결과, 남은 실제 환경 확인만 간결히 알려줘.
```
