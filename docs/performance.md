# 합성 데이터 성능과 PostgreSQL 통합 검증

측정일: 2026-10-04, 로컬 개발 환경. 아래 결과는 **합성 fixture 검증**이며 실제 PUBG 데이터나 운영 호스팅 환경의 측정값이 아니다.

## 측정 환경

| 항목 | 실제 값 |
| --- | --- |
| CPU | Apple M1 Max, arm64 |
| 메모리 | 64 GiB |
| OS | macOS, Darwin 24.6.0 |
| Node | v24.21.0 |
| 분석 동시 실행 | 1개 |
| PostgreSQL | Docker Compose, PostgreSQL 17.6 / aarch64 Linux musl |
| 테스트 DB | 전용 `droplog_test`, 로컬 `127.0.0.1:55432` |

## 순수 분석기 측정

재현 명령:

```sh
node --import tsx scripts/benchmark.ts
```

`scripts/benchmark.ts`는 입력 크기를 직접 계산하고, 큰 fixture가 압축 해제 기준 32 MiB보다 작은지 확인한다. 정규화 결과가 20,000개로 제한되며 `EVENT_LIMIT_EXCEEDED`를 가진 `partial` 리포트인지 검사한다. stdout JSON에는 측정 환경, 입력·결과 크기, 시간, 프로세스 최대 RSS를 출력한다.

2026-10-04 11:09:38 UTC의 결과:

| 항목 | 일반 fixture | 큰 fixture |
| --- | ---: | ---: |
| 입력 이벤트 | 119개 | 25,001개 |
| 입력 JSON 크기 | 34,137 bytes | 23,950,056 bytes, 약 22.84 MiB |
| 정규화 이벤트 | 116개 | 20,000개 |
| 분석 시간 | 워밍업 후 10회 중앙값 1.16 ms, p95 3.96 ms | 1회 86.22 ms |
| 품질 | `ready` | `partial` |
| 누락 안내 | 없음 | `EVENT_LIMIT_EXCEEDED`, 제외 이벤트 5,000개 |

전체 벤치마크 프로세스의 시작 RSS는 95.72 MiB, 최대 RSS는 **250.36 MiB**였다. 최대 RSS에는 fixture 생성, JSON 직렬화로 입력 크기 계산, 정규화와 출력 스키마 검증이 모두 포함된다. 분석 함수 하나의 순수 추가 메모리로 해석하면 안 된다. 큰 fixture는 한 번 측정했으므로 p95로 표시하지 않는다.

이 결과는 순수 동기 분석기만의 값이다. 외부 다운로드, JSON 파싱 전송 계층, HTTP, DB, 브라우저, 실제 PUBG 응답은 포함하지 않는다. 저장된 리포트 API의 p95 목표나 30초 요청 전체 예산을 통과했다는 근거로 사용하지 않는다. 실제 데이터의 분포·장치·호스팅 환경에 따른 재측정이 필요하다.

## 실제 PostgreSQL 통합 테스트

전용 DB 생성은 최초 한 번만 수행한다. 이미 있는 DB를 삭제하거나 초기화하지 않는다.

```sh
docker compose exec -T db createdb -U droplog droplog_test
# TEST_DATABASE_URL을 로컬 비밀 환경변수에 설정한 뒤 실행한다.
pnpm test:integration
```

`TEST_DATABASE_URL`은 `droplog_test`와 같이 이름이 `_test`로 끝나는 전용 데이터베이스를 가리켜야 한다. 환경변수가 없거나 일반 앱 데이터베이스를 지정하면 설명과 함께 실패하며 테스트를 조용히 건너뛰지 않는다. 실제 연결 문자열과 비밀번호는 문서나 테스트 출력에 기록하지 않는다.

`tests/integration/postgres.test.ts`는 Drizzle의 실제 마이그레이션을 사용한다. SQL의 `public` 외래키 참조를 다른 스키마로 바꾸지 않는다. 테스트는 실행마다 무작위 ID를 가진 fixture를 생성하고 종료 시 해당 실행에서 생성한 리포트·플레이어·경기 ID만 삭제한다. 기존 데이터, 테이블과 마이그레이션 이력은 남긴다.

최초 2026-10-04 20:08 KST에는 9개 테스트를 844 ms에 통과했다. `getMatches` 일괄 조회 회귀 검증 추가 후 20:17 KST 최종 실행은 **10개 테스트 통과**, 전체 Vitest 실행 998 ms였다.

- 빈 전용 DB에 체크인된 마이그레이션 적용 및 경기 외래키 검증
- 정규화 경기와 전체 리포트 저장·조회, 새 연결에서 동일 ID 재조회
- 서로 다른 UUID를 가진 10개 동시 저장이 동일 분석 키의 한 행으로 수렴
- 유효성 검증 또는 외래키 실패 시 부분 행을 만들지 않고 기존 리포트 보존
- JSONB에 잘못된 값을 직접 넣었을 때 조회 단계 스키마 검증으로 실패
- 동일 경기 ID의 demo/live 저장 및 조회 분리
- requested name이 null인 플레이어 스냅샷, 출처 구분 및 만료 처리
- 동시 재시도 10건 중 한 건만 획득, 60초 경계에서 다음 재시도 허용
- revision 비교 후 갱신, 오래된 요청으로 ready 리포트를 덮어쓰지 않음
- 일괄 경기 조회의 출처·플랫폼 분리, 원본 ID 순서 복원, 누락 ID 및 null 통계

담당 파일 ESLint와 전체 `pnpm typecheck`도 통과했다. 초기 테스트용 JSONB 손상 입력 바인딩 오류를 수정한 뒤 통합 테스트 전체를 다시 실행한 결과다.

## 남은 실제 환경 검증

이 문서의 표는 합성 벤치마크다. 이후 카카오 랭크 스쿼드 5경기의 실제 다운로드·분석을 수행했으며, 전체 프로세스 최대 RSS 526.69 MiB와 실제 생성 시간·크기는 [전체 검증 기록](validation.md)에 별도로 기록했다. 실제 일반전·다른 모드·Steam과 여러 프로세스·복제본에 대한 호출 제한은 아직 미검증이다.
